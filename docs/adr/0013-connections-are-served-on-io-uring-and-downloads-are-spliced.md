# Connections are served on io_uring, and downloads are spliced

ADR-0010 put file I/O on io_uring through `tokio-uring`, while connections stayed on hyper over tokio's epoll reactor. Profiles under `cargo bench` showed that server CPU was almost all kernel time spent copying cache data: a download was read from the page cache into a user buffer and then written to the socket, so the server copied every byte twice. ADR-0011 rejected `sendfile`/`splice` because hyper owns the connection. The server now owns its connections, so it can splice.

A small io_uring driver (`src/uring`) replaces `tokio-uring`, which has no splice and is unmaintained. A pool of threads (`IO_URING_THREADS`, one per CPU by default) each own a ring. Each thread runs a current-thread tokio runtime with the ring's eventfd registered, so database sockets, timers and channels keep working beside it. Rings use the kernel's default task work mode, where every completion is posted as it happens and fires the eventfd. Deferred task work (`IORING_SETUP_DEFER_TASKRUN`) was tried and dropped. It posts completions only when the thread asks, and in the NixOS VM test (one CPU, Linux 6.18) the eventfd stopped firing after the first deferred completion, which left the ring stalled. Cooperative task work (`IORING_SETUP_COOP_TASKRUN`) also waits for the thread to enter the kernel, so it isn't used either. An operation only queues its entry; the thread's driver task submits everything queued with one `io_uring_enter` and collects completions in the same call. An operation owns its buffers until its completion arrives. One that is dropped early hands them to the ring and is cancelled.

The ring threads share the listening socket. Each serves the connections it accepts with an HTTP/1.1 implementation (`src/uring/server.rs`, heads parsed with `httparse`) in front of the same axum router `axum::serve` runs, so handlers, extractors and routes are unchanged. A request is handled on the thread that accepted it: its socket operations, its handler and the file operations the handler starts all run on one ring, without hops between threads. File operations issued from elsewhere (cleanup, a Merge started with `tokio::spawn`) are handed to a ring thread as before.

- **Downloads** from filesystem storage carry a `FileBody` response extension: the files that hold the payload (the merged object, opened before the response so a missing one is still a 404, or the Parts in order). The server splices them file → pipe → socket, two linked `IORING_OP_SPLICE`s per pipeful, so the second runs as soon as the first completes, in the kernel. Cache data never enters user space; with `MSG_SPLICE_PAGES` (Linux 6.5) the socket takes the page cache's pages rather than copying them. Bodies up to 64 KiB are read and sent with the head in one `sendmsg` instead, because splicing always runs on io_uring's worker threads and a small copy is cheaper than two trips there. The response also carries an ordinary body streaming the same files, used wherever the extension isn't understood: the hyper fallback, tests and other routers. The Storage Reader Lease (ADR-0002) is shared by both and is checked between pipefuls. A lost lease aborts the response, as it aborted the stream before.
- **Uploads** are received straight into the buffers that become body frames: one `recv` per megabyte with `MSG_WAITALL`, never past the end of the body, so the next request on a kept-alive connection stays in the socket. The frames are written with vectored writes as before (ADR-0011). Splicing uploads (socket → pipe → file) was profiled and not built: about 90% of an upload's kernel time is the page cache write, which splice still performs, and the receive copy it would save is the remaining 10%.
- **Everything else** (Twirp, the management API, Results Passthrough) goes through the router unchanged. Responses go out with one `sendmsg` for the head and whatever body frames are ready. Bodies of unknown length are chunked, or delimited by closing the connection for HTTP/1.0 clients.

The server implements what the cache clients and the passthrough need: keep-alive and pipelining, `Content-Length` and chunked request bodies, `Expect: 100-continue`, HEAD, and rejection of malformed or ambiguous framing (a request with both `Transfer-Encoding` and `Content-Length` is served, then the connection is closed). A connection closed before its request body was read lingers briefly, so the response isn't lost to a reset. Graceful shutdown stops accepting, closes idle connections and lets requests in flight finish. HTTP/2 is not offered; `axum::serve` didn't offer it either. `TCP_NODELAY` is set on accepted sockets as before.

Where io_uring is unavailable (`IO_URING=false`, a build without the `io-uring` feature, or a kernel or seccomp profile that refuses a ring at startup, as Docker's default profile does), connections are served by `axum::serve` on hyper and file I/O blocks on tokio's pool, exactly as before. The `STORAGE_FILESYSTEM_IO_URING` and `STORAGE_FILESYSTEM_IO_URING_THREADS` variables still work as aliases for `IO_URING` and `IO_URING_THREADS`. CI runs the whole suite both ways.

Results on the `cargo bench` workloads, from runs interleaved with the previous server (medians of three rounds on a 4-CPU VM):

| Scenario | Wall time | Server CPU |
|---|---|---|
| `actions-cache/restore` | 3.55 s → 2.71 s (−24%) | 9.38 s → 4.22 s (−55%) |
| `actions-cache/save` | 1.67 s → 1.71 s (+2%) | 2.38 s → 2.10 s (−12%) |
| `actions-cache/lookup-misses` | 1.27 s → 1.17 s (−8%) | 2.15 s → 1.54 s (−28%) |
| `buildkit/cold` | 16.41 s → 14.35 s (−13%) | 14.09 s → 11.69 s (−17%) |
| `buildkit/warm` | 0.46 s → 0.39 s (−15%) | 0.62 s → 0.36 s (−42%) |
| `buildkit/change` | 3.40 s → 2.66 s (−22%) | 3.47 s → 2.37 s (−32%) |
| `sccache/cold` | 6.27 s → 6.19 s (−1%) | 8.81 s → 7.98 s (−9%) |
| `sccache/warm` | 2.60 s → 2.46 s (−5%) | 3.24 s → 2.03 s (−37%) |
| `fleet` | 24.07 s → 23.07 s (−4%) | 69.66 s → 56.17 s (−19%) |

Server CPU falls everywhere and most for downloads. Wall time is noisy on a shared VM: single runs vary by tens of percent, so it is the CPU numbers that are reliable. Peak RSS falls in every scenario but `actions-cache/save`, where uploads receive in 1 MiB frames and it rose from about 80–110 MiB to about 140–150 MiB. Per-request latency under the mixed `fleet` load is mixed: lookups and exports are faster, while restores and saves are somewhat slower at the median, because a connection stays on the ring thread that accepted it rather than being work-stolen.

With downloads no longer copying, a profile of `actions-cache/restore` shows the largest remaining server cost is the Merge's `copy_file_range`. On a filesystem without reflinks (ext4) that copy is a full memcpy of every multi-Part archive, while downloads now splice Parts as cheaply as a merged object. Whether the filesystem driver should keep merging is left for a separate decision.
