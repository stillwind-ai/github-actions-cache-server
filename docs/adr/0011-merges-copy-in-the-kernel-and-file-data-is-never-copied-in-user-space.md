# Merges copy in the kernel, and file data is never copied in user space

Profiling the server under load (`cargo bench`, see `benches/README.md`) shows the CPU going almost entirely to the kernel copying bytes between sockets, user buffers and the page cache. User-space code is a few percent, and the largest single item there was our own copying. So the I/O layer is built to copy as little as possible.

A Merge concatenates the Parts with `copy_file_range` on tokio's blocking pool, through the same temp-entry-and-rename and length check as every other write (ADR-0004, ADR-0010). The bytes stay in the kernel, and on filesystems with reflinks (XFS, btrfs) the merged object shares the Parts' extents, so it costs neither copying nor a second copy's worth of disk until `cleanup:parts` runs. This supersedes ADR-0009's note that the filesystem driver "has no server-side copy and always streams". The first download of an unmerged entry no longer tees its Part bytes into the merger: it starts the Merge and streams the Parts like any other Part reader, protected by its Part Reader Lease (ADR-0002). The copy reads the Parts from the page cache the download is already filling, so it no longer costs a userspace pipeline or extra buffers per first download, and a slow client no longer holds a Merge open. io_uring has no `copy_file_range` opcode, which is why the copy runs on the blocking pool.

Most uploads are a single Part: `@actions/cache` sends archives up to 128 MiB as one Put Blob, BuildKit every layer under 1 MiB, sccache every object. Such an upload needs no Merge at all. Upload completion renames its Part to the merged object, inside the transaction that claims the Upload and before the commit, so a Storage Location never names a missing object (which a lookup would purge as dangling, ADR-0005), and records the location as merged with its Parts gone. That saves the copy, the second copy's worth of disk until `cleanup:parts`, and the Merge's seven database statements on the first download; a warm sccache build, a download per compilation unit, runs over three times faster.

Uploads are written as hyper hands over body frames: frames are batched to about 1 MiB and written with one vectored write (`writev`) instead of being copied into a staging buffer. Reads go into a buffer sized to what is left of the file (from `statx` on the open file), which then goes to hyper as-is, so a small file never pins a 1 MiB buffer and the end of a file needs no extra read to find. Without io_uring, file data moves through `std::fs` on tokio's blocking pool rather than `tokio::fs`, which copies every chunk through an internal buffer. The fallback also reads one chunk ahead and writes with `writev`.

Accepted connections set `TCP_NODELAY`. A download's response head usually leaves before its body is read from disk, and with Nagle's algorithm a short body then waits for the client's delayed ACK of the head, about 40 ms.

Rejected: `sendfile`/`splice` from file to socket. It would remove another copy on downloads, but hyper owns the connection and offers no way to hand it a file descriptor, and bypassing hyper for one route would mean reimplementing HTTP/1 framing and keep-alive.
